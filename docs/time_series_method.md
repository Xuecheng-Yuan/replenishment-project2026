# 时间序列预测与动态补货方法

## 1. 研究目标

时间序列阶段只使用历史需求和商品类别，不使用 `x1` 至 `x20`。目标是在总体服务水平不低于 95% 的约束下，使测试窗口周转率尽可能高：

train 和 test 被视为两个任意、不相邻的自然时间窗口。train 只提供增长参数、模型参数和误差比例，不能把第60期的需求水平或模型状态传入 test。

```text
最大化：总销售量 / 平均总期末库存
约束：总销售量 / 总需求量 >= 95%
```

爆品和长尾品分别报告服务水平、周转率和库存，但当前不设置分类硬约束。

## 2. 候选模型

代码只保留结构清楚、能够用60期短序列稳定估计的方法：

- Naive；
- 3、6、12期移动平均；
- 12期漂移模型；
- 12期局部线性趋势；
- 简单指数平滑；
- 阻尼 Holt 趋势；
- ARIMA(1,1,0) 的条件最小二乘实现；
- 分层共同趋势：先预测类别总需求，再按SKU近期份额分配。

train 中零需求比例很低，长尾品并不是典型间歇需求，因此暂不使用 Croston、SBA 或 TSB。所有模型参数都集中写在 `configs/time_series.yaml`，便于合作者修改。

## 3. 滚动验证

60期 train 设置三个扩展窗口：

| 验证折 | 历史期 | 验证期 |
|---|---|---|
| 1 | 1–30 | 31–40 |
| 2 | 1–40 | 41–50 |
| 3 | 1–50 | 51–60 |

每个验证块都重新冷启动：第1期只用于确定新窗口的需求水平，从第2期开始评价预测和补货。每次预测第 `t+1` 期时只能使用该窗口第 `t` 期及以前的数据。

候选方法必须在每一个验证折都达到95%总体服务水平。可行方法中，按照三个验证窗口合并后的周转率选择最高者，而不是按照 WAPE 或样本内拟合优度选择。

## 4. 动态安全库存

对类别 `g` 中的 SKU `i`，下一期目标库存为：

```text
B(i,t+1) = ceil(max(0, forecast(i,t+1) + z(g) * scale(i,t+1)))
```

其中：

- `forecast` 是严格的一步预测；
- `z(g)` 是爆品或长尾品的安全系数，只在 train 滚动验证中选择；
- `scale` 使用最近12期一步预测的滚动 WAPE（绝对误差之和除以实际需求之和），并随当前预测量同比例变化。

这一误差尺度能够随需求增长更新，比使用早期固定残差标准差更适合当前数据。安全系数在 `[0, 4]` 上以 `0.25` 为步长搜索。

## 5. 库存时序

当前提前期为1期，每期顺序固定为：

1. 接收上一期订单；
2. 本期需求发生，库存不足部分记为 lost sales；
3. 计算期末库存；
4. 按下一期目标库存下单；
5. 订单在下一期期初到达。

test 第一期开仓库存严格来自 test 文件的 `initial_inventory`，模型不能补写期初订单。第1期需求观察后，模型以该需求建立 test 自身的水平，并用 train 学到的分类增长率预测第2期；此后只使用已经观察到的 test 历史滚动更新。

## 6. 防止数据泄漏

1. 先读取 train，完成模型、安全系数和最终方法选择；
2. 参数冻结后才读取 test；
3. test 第 `t` 期真实需求只能更新第 `t+1` 期预测；
4. train 第60期的绝对水平和模型状态不会传入 test；
5. test 指标不会回流到任何参数选择；
6. 输出 JSON 保存 train/test 文件指纹和用途。

## 7. 运行与输出

```bash
python -m experiments.run_time_series
```

只生成三份结果，避免重复保存大规模逐期轨迹：

- `time_series_comparison.csv`：所有冻结候选的 train 验证和 test 汇总；test 列只报告、不反向选模型；
- `time_series_test_per_item_metrics.csv`：最终模型的SKU测试指标；
- `time_series_summary.json`：最终模型、参数、数据边界及总体/分类测试指标。

在本地结果审核通过前，不提交也不推送 GitHub。

## 8. 实验结果

原连续时期实验使用了错误的状态传递假设，已经撤销。按独立自然时间窗口冷启动后，train 滚动验证选择了 Naive，安全系数为爆品 `0.00`、长尾品 `0.25`：

| 指标 | 结果 |
|---|---:|
| train 验证综合服务水平 | 95.7228% |
| train 最差验证折服务水平 | 95.0360% |
| test 总体服务水平 | 91.3073% |
| test 总体周转率 | 480.2537 |
| test 平均总期末库存 | 171,995.57 |
| 是否满足95%约束 | 否 |

十个冻结候选在 test 均未达到95%，服务水平最高的是12期漂移模型，为93.2138%。这说明冷启动解决了窗口水平不连续问题，但 train 学到的增长规律和刚好越过95%的库存缓冲仍无法覆盖 test 的增长变化。

这些 test 结果只用于评价，不能据此重新提高安全系数或反选模型。下一轮如需引入更保守的服务余量，必须先明确写成 train-only 规则，然后不再使用当前 test 调参。
