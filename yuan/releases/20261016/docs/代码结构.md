# 代码阅读顺序

## 先理解一条最短路径

```text
run.py prepare → data.py → 当前运行/data/input.npz
run.py train   → training/pipeline.py → 模型拟合、验证选参、最终重拟合
run.py evaluate→ inference.py → evaluation.py → summary.json与SKU指标
run.py compare → results/comparison.csv
```

`run.py`只处理命令；`registry.py`只管理模型清单；`runtime.py`只管路径与保存。这些文件不藏模型算法。

## 从baseline开始看

1. 在 `training/forecast.py` 找 `history_prediction` 中 `kind == 'baseline'`：逐SKU历史需求均值、标准差。
2. 看 `training/pipeline.py:train_forecast`：验证选择z，最终用60期重算统计量。
3. 看 `evaluation.py:target_policy`：`目标=均值+z×尺度`，`订单=max(目标−当前库存,0)`。当s=S时它是订货至目标库存策略，没有单独的触发缓冲区。
4. 看 `evaluation.py:simulate`：为什么今天下单不能满足今天需求。
5. 看 `evaluation.py:metrics`：三个指标怎样计算。

## 每组模型的位置

- 历史统计：`training/forecast.py:history_prediction`。5种方法共用仿真和标定，不复制5套入口。
- ML：`models/<模型>.py:build`负责真实估计器；`training/forecast.py:ml_fit/ml_bundle`负责公共拟合与残差尺度。
- SPO：`models/spo_linear.py`、`xgboost_spo.py`、`lightgbm_spo.py`、`direct_lightgbm.py`保存真实损失；`training/decision.py`负责训练数据、动作代价与订单策略。
- 神经网络/DFL：`training/neural.py`中的`DemandNet`、`DirectNet`、`inner`、`fine_tune`和`runtime_policy`。模型差异在训练期数、内层参数化和是否在线更新，不需复制相同网络5次。
- MPC：`training/mpc.py`，包含训练前缀聚类、四步需求预测、四期情景优化。
- 融合：`training/ensemble.py`，包括单纯形投影、全局权重、逐SKU权重、分组及硬路由。14个需求预测专家参与，不把SPO/DFL订单硬加到需求上。

## 为什么有些模型不各占一个完整训练文件

线性回归与Ridge的差异是估计器，不是Excel读取或库存时序。复制整份训练文件会产生两份同名指标、两套时序和难以同步的修复。本包让差异集中，公共流程唯一。每个模型的中文文档仍独立，能从模型索引直接定位。

## 想修改时改哪里

- 改ML候选：`training/forecast.py:GRID`，不是改reference中的历史参数。
- 改服务区间：`evaluation.py:LOW/HIGH`；神经网络/MPC目标也有同一研究区间的显式常量。若改任务标准，必须同步改损失并另开运行目录，不能只改评价器。当前提交固定95%—96%，不提供误导性的单边开关。
- 改原始动作网格：`training/decision.py:ACTIONS`；细化规则在`training/action_grid.py`，推理读取模型冻结的actions。必须重新训练，不允许只改展示参数。
- 改输出目录：命令行`--workdir`，不要修改源码路径。
- 新增模型：实现其估计器或策略，登记`registry.py`并接入统一训练/推理，补上测试和文档。
