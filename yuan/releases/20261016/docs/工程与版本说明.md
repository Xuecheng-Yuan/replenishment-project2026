# 工程与版本说明

## 一份目录，三个边界

- `replenishment/`：Yuan个人29方案的算法实现，共享输入、特征和评价器。相同家族共用训练框架，不为每个名称复制整套流水线。
- `partners/kristina/upstream/`：Kristina固定Git提交的选择性源码和结果快照，保留原始路径、署名和哈希，不混入个人训练包。
- `artifacts/`与`results/benchmark/`：既有正式结果的冻结回放与重新计量，不是本次新训练的成绩。

`configs/model_catalog.json`是35个展示方案的唯一索引。每项指向代码、中文说明、冻结参数、轨迹；网站和文档从该索引生成。`run.py list/train/evaluate`只操作个人29方案；Kristina复现入口见她的独立README。

## 版本选择规则

个人主要模型沿用前42期拟合、后18期验证，预热回放后评分；最终用60期重新拟合。不是今天桌面项目使用的36/24冷启动方案，也不纳入那两个项目的预测结果。SPO采用训练内部动作细化实验中**验证选中**的版本，而非逐模型挑测试最好的一行。XGBoost-SPO保留原动作集合；其余四种选中细化集合。新增训练代码保留已采用的原版/细化配方，不为未采纳消融再复制训练器。

本版不因测试未达标而偷偷换回旧版本；例如直接决策LightGBM约93.73%的测试服务水平明确标记未达标。DFL提高满足率的候选增加库存，不满足指定约束，因此仅在研究记录中展示。

Kristina取Git提交`aec11c863b6d8a71a1e0874cfb60594cc034cf51`。正式指标使用`experiments/service95_revision/outputs_v4`六方法；最新`constraint_mechanism`是诊断，未取代正式结果。她的训练内部包含回溯重启校准，不等同于个人前向验证，不能把共同指标说成完全相同的实验协议。

## 训练、冻结、评价分离

1. `prepare`核验输入形状、库存、非负需求和时间长度，保存输入哈希。
2. `train`使用训练数据；训练分支屏蔽测试需求及测试x，验证选参后保存参数和权重。
3. 独立模型的冻结记录保存算法源码、输入和模型身份，resume检查源码身份。四个融合方案共用meta与专家缓存，不共用这一份逐模型冻结文件，因此也应严格另开workdir，不跨代码版本复用运行目录；缓存完整身份保护不是本轮已完成的保证。
4. `evaluate`顺序回放，每次只能使用已发生的数据；统一计算库存、销量和三项指标。
5. `reference/replay`只查看发布附件，不会运行模型，更不会把冻结成绩冒充新训练。

首次运行未保证与历史训练逐位一致：库版本、随机数、树模型线程和浮点运算均可能影响训练。真实冻结SPO权重的推理逐位复现，与全规模重新训练是不同证据。

## 结果不能越界解读

服务水平是SKU×周期等权的期末库存>0比例，不是Fill Rate，不是逐SKU95%硬约束。库存需求比J为总期末库存/总需求，越低越好，不是传统意义的周转次数。测试曾被反复查看，不应称为全新外部盲测。帕累托曲线只连接当前有限方案的经验点，不提供理论最优保证。

网站不训练模型、不联网取数；改变SKU、周期和负责人只读取本地已冻结轨迹。完整轨迹、匿名特征及原始需求仍可能属于研究数据，公开前应确认共享权限。
